# Research: CompanionDeviceManager association and presence

> Gathered 2026-10-03 by a research agent reading live primary sources. Every finding was then re-checked by an independent verifier; its verdict is shown on each finding.
> This file is evidence for the ADRs. It records what was true on that date and is not kept current.

## Summary

Research only; no project files were created or modified. (The relayed housekeeping request is already satisfied on disk: CLAUDE.md and README.md already point at docs/... and docs/adr/, so I left them alone.)

Bottom line: CompanionDeviceManager (CDM) presence is worth using, but as one of two equal triggers, not as the sole or authoritative one. For a classic (BR/EDR) head unit, CDM "appeared" has been driven by the ACL connection since Android 12 (API 31); no BLE advertising is needed. However, CDM gets that signal from exactly the same Bluetooth-stack call site that sends ACTION_ACL_CONNECTED, so it is an independent delivery path (system_server binds your service directly), not an independent detector. Its real value is: (1) it starts a dead or even force-stopped app by binding CompanionDeviceService, (2) an association plus REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND gives a standing background foreground-service-start exemption that does not depend on the truck being connected, (3) REQUEST_COMPANION_RUN_IN_BACKGROUND puts the app on the battery-optimisation allowlist without a prompt (permanently on Android 12-15), and (4) it exempts the app from unused-app permission auto-revoke.

Behaviour differs a lot by version (all read from AOSP release branches): Android 12 has a bug where "disappeared" never fires for connections shorter than 10 minutes; Android 13 does not rebind after process death and loses a connect that happens before first unlock; Android 14+ rebinds after 10 s and defers pre-unlock events; Android 15+ sends events per source; Android 16 introduces onDevicePresenceEvent/ObservingDevicePresenceRequest, deprecates the older calls, and strips the battery allowlist entry on every disconnect (fixed in Android 17). The project docs say the target phone is a Xiaomi POCO X5 on Android 14 (HyperOS), so the Android 14 column is what will actually run; whether HyperOS Autostart gating blocks the CDM bind could not be confirmed from any source and must be tested on the phone.

Limits of this research: issuetracker.google.com could not be read (WebFetch gets a sign-in wall, the browser pane blocks the domain), so there are no issue-tracker citations. Bug findings come from reading AOSP source and a few GitHub reports; I found no confirmed Samsung One UI-specific CDM defect. Newest released Android appears to be 17 (API 37): developer.android.com lists it under Releases with "Added in API level 37" entries and AOSP has an android17-release branch.

## Findings

### 1. To associate an already-paired classic head unit you must use BluetoothDeviceFilter.Builder().setAddress(MAC) together with AssociationRequest.Builder().setSingleDevice(true); only that combination makes the system look in the bonded-device list.

CompanionDeviceDiscoveryService.checkBoundDevicesIfNeeded() returns early unless the request is single-device AND a Bluetooth filter has a non-empty address; only then does it match against BluetoothAdapter.getBondedDevices() (plus GATT-connected devices). Same logic in android12-release, android14-release and android17-release. With that combination the truck is found immediately even when it is switched off. Without it, the CDM app runs classic inquiry plus BLE/Wi-Fi scans and a head unit that is not in pairing/discoverable mode will not be found (20 s timeout). No device profile applies: DEVICE_PROFILE_AUTOMOTIVE_PROJECTION needs REQUEST_COMPANION_PROFILE_AUTOMOTIVE_PROJECTION, which is protectionLevel internal|role and documented as not for third-party apps, so leave the profile unset. Getting the MAC from the paired list needs the BLUETOOTH_CONNECT runtime permission.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/packages/CompanionDeviceManager/src/com/android/companiondevicemanager/CompanionDeviceDiscoveryService.java
- Verifier: **confirmed**. Confirmed in two primary sources. The setSingleDevice() reference says bonded devices are also searched when a single device is requested with a specific BluetoothDeviceFilter MAC. The discovery service source has the same condition in android12, 13, 14, 16 and 17. Nuance: on Android 12-15 the bonded lookup returns void and the classic inquiry plus BLE/Wi-Fi scans still start alongside it; only Android 16+ skips discovery when the bonded match is found. DEVICE_PROFILE_AUTOMOTIVE_PROJECTION is internal|role and marked not for third-party apps in the android17 manifest. getBondedDevices() needs BLUETOOTH_CONNECT. (https://developer.android.com/reference/android/companion/AssociationRequest.Builder)

### 2. The association call and its callbacks differ at API 33, and the user sees a single one-time system consent dialog.

API 31-32: associate(request, Callback, Handler); Callback.onDeviceFound(IntentSender) -> startIntentSenderForResult; result Intent carries EXTRA_DEVICE (BluetoothDevice). API 33+: associate(request, Executor, Callback) with onAssociationPending(IntentSender) (rename of onDeviceFound, deprecated in 33) and onAssociationCreated(AssociationInfo) giving the association id and MAC; getMyAssociations() and disassociate(int) replace the String-based getAssociations()/disassociate(String). onFailure(int, CharSequence) was added in API 36. The manifest needs <uses-feature android:name="android.software.companion_device_setup"/>. For a single device with no profile the AOSP dialog text is "Allow <app> to manage your <device>" on Android 12 and "Allow <app> to access <device>?" on Android 13+ (Android 17: "Allow the app <app> to access <device>?") with Allow / Don't allow buttons (strings.xml in packages/CompanionDeviceManager). OEM skins may restyle it. The association is removed only by disassociate(), uninstall, or clearing app data.

- Confidence: high · Applies to: API 31-37
- Source: https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing
- Verifier: **confirmed**. API levels and callbacks are confirmed on the reference pages (associate with Executor, onAssociationPending, onAssociationCreated, getMyAssociations, disassociate(int) all API 33; onFailure(int, CharSequence) API 36; EXTRA_DEVICE deprecated 33). Two details are wrong. (1) Dialog text: Android 13 reads "Allow <app> to access your <device>" with no question mark; "Allow <app> to access <device>?" starts at Android 14; Android 17 reads "Allow the app <app> to access <device>?". (2) The association is NOT removed only by disassociate(), uninstall or clear-data. AOSP Settings has a companion-apps section on the Bluetooth device details page with a Remove button that calls disassociate/legacyDisassociate (present in android12, 14 and 17). Also, Android 12's PackageMonitor has no onPackageDataCleared handler, so clear-data does not remove it there. (https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/android17-release/src/com/android/settings/bluetooth/BluetoothDetailsCompanionAppsController.java)

### 3. On Android 16+ the association flow no longer reports discovery timeouts to the app.

Apps running on Android 16 are not sent RESULT_DISCOVERY_TIMEOUT; the user sees a timeout dialog and the app receives RESULT_USER_REJECTED when it is dismissed. The search window was extended beyond 20 s (AOSP 17 source shows a 20 s soft and 5 minute hard timeout). Irrelevant when the bonded-device shortcut (address filter + single device) is used, because the match is immediate, but the onboarding error handling should not assume a timeout code.

- Confidence: high · Applies to: API 36+
- Source: https://developer.android.com/about/versions/16/behavior-changes-all
- Verifier: **confirmed**. Confirmed verbatim on the Android 16 behavior-changes page (RESULT_DISCOVERY_TIMEOUT no longer sent; RESULT_USER_REJECTED after the user dismisses the timeout dialog; search extended beyond 20 s). android17 source has TIMEOUT_SOFT = 20_000 and TIMEOUT_HARD = 300_000. (https://developer.android.com/about/versions/16/behavior-changes-all)

### 4. Presence-observation methods: the String overloads arrived in API 31 and were deprecated in API 36; the ObservingDevicePresenceRequest overloads arrived in API 36.

startObservingDevicePresence(String deviceAddress) and stopObservingDevicePresence(String): added API 31, deprecated API 36; the argument is the MAC address of an already-associated device (throws DeviceNotAssociatedException otherwise). startObservingDevicePresence(ObservingDevicePresenceRequest) / stopObservingDevicePresence(ObservingDevicePresenceRequest): added API 36. ObservingDevicePresenceRequest.Builder (API 36) has setAssociationId(int) (usable by any companion app) and setUuid(ParcelUuid), which needs REQUEST_OBSERVE_DEVICE_UUID_PRESENCE (signature|privileged) plus the automotive-projection profile, so it is not available to MilO. All of them require the normal permission REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE. In android16-release the deprecated String method simply resolves the association and calls the new path, so it still works on 16/17. Starting observation while the device is already connected fires the callback immediately on Android 13+.

- Confidence: high · Applies to: API 31-37
- Source: https://developer.android.com/reference/android/companion/CompanionDeviceManager
- Verifier: **confirmed**. API levels, the setUuid restriction (REQUEST_OBSERVE_DEVICE_UUID_PRESENCE is signature|privileged plus automotive-projection profile) and the String-to-new-path forwarding in android16 are confirmed. One detail is wrong: starting observation while the device is already connected does NOT fire a callback on Android 15 and 16. There the 'already present' branch calls onDevicePresenceEvent, the per-source set add() returns false, and the notify is gated on `isSelfManaged() || added`, so the service is bound but no event or legacy callback is delivered. Worse, if the association existed unobserved when the truck connected, BluetoothDeviceProcessor skipped it (`if (!association.isNotifyOnDeviceNearby()) continue`), so nothing happens until the next reconnect. Android 13/14 do fire the callback; Android 17 fixes both cases (forceNotification plus a live BluetoothDevice.isConnected() check). (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/companion/java/com/android/server/companion/devicepresence/DevicePresenceProcessor.java)

### 5. CompanionDeviceService callbacks: String variants (API 31, deprecated 33), AssociationInfo variants (API 33, deprecated 36), onDevicePresenceEvent(DevicePresenceEvent) (API 36).

onDeviceAppeared(String)/onDeviceDisappeared(String): added 31, deprecated 33. onDeviceAppeared(AssociationInfo)/onDeviceDisappeared(AssociationInfo): added 33, deprecated 36; their default implementation forwards to the String variant for non-self-managed associations. onDevicePresenceEvent(DevicePresenceEvent): added 36. Android 12 calls the String variant; Android 13-14 call the AssociationInfo variant. From android15-release onward the server sends the new event and then ALSO the legacy callback for every event (legacyNotifyDevicePresenceEvent, comment "Also send the legacy callback"), so an app overriding both gets each event twice on 16+ (and possibly on 15 if the device_presence flag is on). Handlers must therefore be idempotent rather than branching only on SDK_INT. All callbacks arrive on the main thread; onBind is final.

- Confidence: high · Applies to: API 31-37
- Source: https://developer.android.com/reference/android/companion/CompanionDeviceService
- Verifier: **confirmed**. Confirmed on the reference page and in source. android15/16/17 DevicePresenceProcessor sends notifyDevicePresenceEvent and then legacyNotifyDevicePresenceEvent unconditionally; the app-side stub gates the new callback on Flags.devicePresence(). Added nuance: the app-side stub delivers every callback with mMainHandler.postAtFrontOfQueue, so two callbacks that arrive while the main thread is busy (for example during a cold start) run in reverse order. That strengthens the case for idempotent handlers that re-check real state. (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/core/java/android/companion/CompanionDeviceService.java)

### 6. DevicePresenceEvent (API 36) distinguishes BLE sightings from Bluetooth connections; the legacy callbacks do not.

Constants: EVENT_BLE_APPEARED=0, EVENT_BLE_DISAPPEARED=1, EVENT_BT_CONNECTED=2, EVENT_BT_DISCONNECTED=3, EVENT_SELF_MANAGED_APPEARED=4, EVENT_SELF_MANAGED_DISAPPEARED=5 (all API 36), EVENT_ASSOCIATION_REMOVED=6 (36.1), EVENT_SELF_MANAGED_NEARBY=7 and EVENT_SELF_MANAGED_NOT_NEARBY=8 (API 37), NO_ASSOCIATION=-1. For the truck, EVENT_BT_CONNECTED / EVENT_BT_DISCONNECTED are the ones that matter. On API 31-35 the app only gets appeared/disappeared with no indication of source.

- Confidence: high · Applies to: API 36+
- Source: https://developer.android.com/reference/android/companion/DevicePresenceEvent
- Verifier: **confirmed**. All constants, values and API levels match the reference page exactly (0-5 at API 36, EVENT_ASSOCIATION_REMOVED=6 at 36.1, 7 and 8 at API 37, NO_ASSOCIATION=-1). (https://developer.android.com/reference/android/companion/DevicePresenceEvent)

### 7. Exact manifest declaration and permission protection levels.

Service: <service android:name=".X" android:exported="true" android:permission="android.permission.BIND_COMPANION_DEVICE_SERVICE"><intent-filter><action android:name="android.companion.CompanionDeviceService"/></intent-filter></service>. Declare exactly one such service (Android 12 refuses to bind if the package has more or fewer than one; later versions pick a primary, selectable with the android.companion.PROPERTY_PRIMARY_COMPANION_DEVICE_SERVICE property). Protection levels in android17-release core/res/AndroidManifest.xml: BIND_COMPANION_DEVICE_SERVICE = signature (only the system can bind); REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE = normal (API 31); REQUEST_COMPANION_RUN_IN_BACKGROUND = normal (API 26; docs say it implies the FGS-from-background permission); REQUEST_COMPANION_USE_DATA_IN_BACKGROUND = normal (API 26); REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND = normal (API 31). All four REQUEST_* are install-time permissions with no user prompt. USE_DATA_IN_BACKGROUND only affects metered-data policy and is not needed for an app with no backend.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/core/res/AndroidManifest.xml

Protection levels and API levels match android17 core/res/AndroidManifest.xml and the Manifest.permission reference. Android 12 does return a NoOp connector unless the package has exactly one service (`packageResolveInfos.size() != 1`). (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/core/res/AndroidManifest.xml)

### 8. A classic ACL connection has counted as "appeared" since Android 12 (API 31), the first release with presence observation; a head unit that never advertises over BLE still triggers it.

android12-release CompanionDeviceManagerService registers BluetoothAdapter.registerBluetoothConnectionCallback() at boot and its onDeviceConnected(address) calls onDeviceNearby(address), which sends onDeviceAppeared to observing associations; a separate BLE scan (filtered by association MAC) feeds the same method. The API 31 SDK javadoc already says "For Bluetooth classic devices this is triggered when the device connects/disconnects." The same connection-callback design is present in android13 (BluetoothCompanionDeviceConnectionListener), android14, android15/16/17 (BluetoothDeviceProcessor -> EVENT_BT_CONNECTED). Presence is keyed purely on the association's MAC address.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/companion/java/com/android/server/companion/CompanionDeviceManagerService.java
- Verifier: **confirmed**. Confirmed in android12-release source (registerBluetoothConnectionCallback at PHASE_SYSTEM_SERVICES_READY; onDeviceConnected calls onDeviceNearby, which sends onDeviceAppeared) and in the android12 javadoc line "For Bluetooth classic devices this is triggered when the device connects/disconnects." Same design verified in android13, 14, 15, 16 and 17. (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/companion/java/com/android/server/companion/CompanionDeviceManagerService.java)

### 9. CDM's Bluetooth trigger and the ACTION_ACL_CONNECTED broadcast come from the same call site in the Bluetooth stack, so CDM is a second delivery path, not a second detector.

RemoteDevices.aclStateChangeCallback() builds the ACL_CONNECTED/ACL_DISCONNECTED intent, sends it, and then invokes every registered IBluetoothConnectionCallback (the callback CDM registers) in the same method. Verified in android12-release (packages/apps/Bluetooth), android14, android16 and android17 (packages/modules/Bluetooth). If the Bluetooth stack never reports the ACL (or reports it late), both paths miss it together. What differs is delivery: the broadcast goes through the broadcast queue to a manifest receiver; CDM has system_server bind the service directly.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/android17-release/android/app/src/com/android/bluetooth/btservice/RemoteDevices.java
- Verifier: **confirmed**. Confirmed in RemoteDevices.aclStateChangeCallback() for android12 (packages/apps/Bluetooth), android14, android16 and android17: the intent is broadcast and then the IBluetoothConnectionCallback list is invoked in the same method, and both are skipped if the intent is null. (https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/android17-release/android/app/src/com/android/bluetooth/btservice/RemoteDevices.java)

### 10. If the head unit is dual-mode and advertises BLE with the same address, legacy "appeared" can fire from a BLE sighting rather than the ACL connection, and on Android 13/14 the later ACL connect then produces no callback at all.

The system runs a BLE scan filtered on the MAC of every observed association whenever Bluetooth (or Bluetooth scanning) is on. In android13/14 CompanionDevicePresenceMonitor.onDevicePresent() returns without a callback if the device is already present from another source ("if (alreadyPresent) return"), so BLE-then-ACL yields one appeared (at BLE time) and nothing at connect. On Bluetooth disconnect Android 14 also clears the BLE presence and reports disappeared immediately, after which continued BLE advertising can re-trigger appeared. Android 15+ reports each source separately and API 36+ labels them. Practical impact is unknown for this truck (many head units use a different or random LE address), which is why legacy appeared should be confirmed against real connection state before starting a trip.

- Confidence: medium · Applies to: API 33-35 (legacy callbacks); API 36+ can distinguish
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/companion/java/com/android/server/companion/presence/CompanionDevicePresenceMonitor.java
- Verifier: **confirmed**. Confirmed by source reading (not a device test). android13/14 CompanionDevicePresenceMonitor.onDevicePresent has `if (alreadyPresent) return;`. android14 onBluetoothCompanionDeviceDisconnected removes the BLE entry first and then reports gone. android15+ tracks each source separately. (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/companion/java/com/android/server/companion/presence/CompanionDevicePresenceMonitor.java)

### 11. Yes, the system starts a dead app process to deliver the callback, and keeps the service bound for as long as the device is present; how long after that varies by version.

CDM binds through ServiceConnector, which always adds Context.BIND_AUTO_CREATE, so the process and service are created if not running (the API docs say "The app doesn't need to remain running in order to receive its callbacks"). Android 12/12L: flag BIND_IMPORTANT; stays bound until 10 minutes after disappeared (DEVICE_DISAPPEARED_UNBIND_TIMEOUT_MS). Android 13: flag BIND_ALMOST_PERCEPTIBLE (oom adj 225, "as important as a perceptible app"); unbound immediately after the disappeared callback. Android 14-17: same flag; unbind is posted 5 s after disappeared (UNBIND_POST_DELAY_MS = 5_000). For a classic device "present" means ACL connected, so the binding lasts for the Bluetooth connection plus 0 s / 5 s / 10 min. The binding raises process priority but is not a foreground service; a disconnect grace period will outlive the binding on Android 13+, so the app's own foreground service must already be running.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/companion/java/com/android/server/companion/CompanionDeviceServiceConnector.java
- Verifier: **confirmed**. Bind flags and unbind timings are confirmed (ServiceConnector adds BIND_AUTO_CREATE; Android 12 BIND_IMPORTANT with 10 min unbind; Android 13 immediate postUnbind; Android 14-17 UNBIND_POST_DELAY_MS = 5_000). Two small corrections. (1) The oom adj of 225 (PERCEPTIBLE_MEDIUM_APP_ADJ) is Android 13 only; Android 14's OomAdjuster gives BIND_ALMOST_PERCEPTIBLE without BIND_NOT_FOREGROUND PERCEPTIBLE_APP_ADJ + 1 = 201. (2) On Android 12 the 10-minute unbind is only scheduled inside onDeviceDisappeared, so when disappeared is never delivered (the short-trip bug) the service simply stays bound. (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/core/java/com/android/server/am/OomAdjuster.java)

### 12. Rebinding after the app process dies while the truck is connected: 10 s on Android 12, not at all on Android 13, 10 s on Android 14-17, and the appeared event is not re-sent.

android12: binderDied() posts a reconnect after DEVICE_LISTENER_DIED_REBIND_TIMEOUT_MS (10 s). android13: onCompanionApplicationBindingDiedInternal() contains "TODO(b/218613015): implement" and returns false, so there is no rebind until the next disconnect/reconnect. android14-17: shouldScheduleRebind() is true for non-self-managed associations with notifyOnDeviceNearby ("Always rebind for non-selfManaged devices") and the connector is reconnected after REBIND_TIMEOUT = 10 s. The rebind only calls serviceConnector.connect(); no new onDeviceAppeared/onDevicePresenceEvent is delivered, so CompanionDeviceService.onCreate() is the only hook the app gets and should be used to check whether a trip needs resuming.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/companion/java/com/android/server/companion/CompanionApplicationController.java
- Verifier: **confirmed**. Confirmed: android12 binderDied posts connect after 10 s; android13 has `TODO(b/218613015): implement` and returns false; android14-17 shouldScheduleRebind is true for non-self-managed observed associations and onRebindingCompanionApplicationTimeout only calls serviceConnector.connect(). Note the 14+ rebind does not check whether the device is still present. (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/services/companion/java/com/android/server/companion/devicepresence/CompanionAppBinder.java)

### 13. Associations and the observe flag survive reboot; a connection that happens before the first unlock is lost on Android 13 and deferred to unlock on Android 14+.

Associations are persisted per user in /data/system_de/<user>/companion_device_manager.xml including the notify_device_nearby attribute (AssociationDiskStore), and the Bluetooth connection callback is re-registered at boot, so nothing has to be re-registered by the app. android14 BluetoothCompanionDeviceConnectionListener parks connect events in mPendingConnectedDevices while the user is not unlocking/unlocked and CompanionDeviceManagerService.onUserUnlocked() replays them; android15-17 do the same via onDeviceLocked()/sendDevicePresenceEventOnUnlocked(). android13 has no such logic: the bind fails before unlock and the device is already marked present, so no appeared arrives until the next reconnect. Related report: android/platform-samples issue 159 (BLE device, Android 13 Pixel 6a / Nothing Phone 2 / OnePlus 8 Pro stop getting onDeviceAppeared after reboot; Samsung S20/S23 fine), closed as stale with no maintainer answer.

- Confidence: medium · Applies to: API 33 vs API 34-37
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/companion/java/com/android/server/companion/presence/BluetoothCompanionDeviceConnectionListener.java
- Verifier: **confirmed**. Android 14+ deferral is confirmed in source (mPendingConnectedDevices replayed in onUserUnlocked; android15-17 onDeviceLocked / sendDevicePresenceEventOnUnlocked). The Android 13 loss is a source inference, not a test: there is no pending logic, and bindCompanionApplication returns early when the per-user service register finds no eligible service. Minor: the /data/system_de path applies from Android 13; Android 12 stores associations in the legacy companion_device_manager_associations.xml under the user system directory (the notify_device_nearby attribute exists there too). (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/companion/java/com/android/server/companion/presence/BluetoothCompanionDeviceConnectionListener.java)

### 14. Associations survive app updates and force-stop; only uninstall or clearing app data removes them. A CDM bind restarts a force-stopped app on AOSP, which a manifest broadcast cannot do.

CompanionDeviceManagerService's PackageMonitor removes associations only in onPackageRemoved and onPackageDataCleared (updates raise onPackageModified, which just refreshes exemptions). There is no force-stop handler. When system_server binds the service, ActiveServices.bringUpServiceInnerLocked() calls notifyComponentUsed()/setPackageStoppedState(false), taking the package out of the stopped state. Broadcasts, by contrast, exclude stopped packages by default, so a manifest ACL_CONNECTED receiver stays silent after a force-stop until the app is opened. A reinstall that requires uninstalling first (for example a different debug signing key) deletes the association and the user must re-associate. Self-managed associations idle for 90 days are auto-removed, but that rule does not apply to a normal MAC-based association. Whether an OEM skin's force-stop/"deep sleep" honours the bind was not verified.

- Confidence: medium · Applies to: API 31-37 (AOSP behaviour)
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/services/companion/java/com/android/server/companion/CompanionDeviceManagerService.java
- Verifier: **confirmed**. Update and force-stop survival and the un-stop on bind are confirmed (android17 bringUpService calls notifyComponentUsed, which calls setPackageStoppedState(false); android12/14 call setPackageStoppedState directly). Correction to 'only uninstall or clearing app data removes them': the user can also remove the association from the Bluetooth device details page in system Settings, and Android 12 does not remove it on clear-data. The 90-day idle rule is confirmed as self-managed only (`if (!association.isSelfManaged()) continue;`). (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/services/core/java/com/android/server/pm/PackageManagerService.java)

### 15. Android 12/12L bug: onDeviceDisappeared is not delivered when a classic device disconnects after being connected for less than 10 minutes.

In android12-release onDeviceDisconnected() only calls onDeviceDisappeared() if isDeviceDisappeared(lastSeen), which is true only when the last-nearby timestamp is at least DEVICE_DISAPPEARED_UNBIND_TIMEOUT_MS (10 minutes) old. For a classic-only device that timestamp is the connect time, and the one-shot 10 s TriggerDeviceDisappearedRunnable has already run and done nothing because the device was still connected. Result: short trips never get a CDM disappeared on API 31/32. android12L-release is identical in this area. This is from source reading, not a device test. It makes ACL_DISCONNECTED the necessary trip-end signal on those versions.

- Confidence: medium · Applies to: API 31-32
- Source: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/companion/java/com/android/server/companion/CompanionDeviceManagerService.java
- Verifier: **confirmed**. Confirmed by source in both android12-release and android12L-release: onDeviceDisconnected only calls onDeviceDisappeared when isDeviceDisappeared(lastSeen) is true, which requires the last-nearby timestamp to be at least DEVICE_DISAPPEARED_UNBIND_TIMEOUT_MS (10 min) old, and the one-shot 10 s runnable does nothing while connected. Source reading only; no device test or public bug report found. (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12L-release/services/companion/java/com/android/server/companion/CompanionDeviceManagerService.java)

### 16. CDM tracks connected devices in an in-memory map keyed by MAC and silently drops a connect it believes is a duplicate, which is a possible stuck-state failure mode.

BluetoothDeviceProcessor.onDeviceConnected(): if mAllConnectedDevices.put(mac, device) != null it returns (Android 17 logs "already marked as connected. Skipping duplicate event"). If a disconnect callback is ever missed (for example a Bluetooth process crash), later connects for that MAC are ignored until system_server restarts. The map is also transport-agnostic: for a dual-mode device the second transport's connect is ignored and the first transport to drop reports the whole device as disconnected. I found no public bug report confirming this in the field; it is an inference from the code and a reason not to make CDM the only trigger.

- Confidence: low · Applies to: API 33-37

### 19. CDM manipulates the battery-optimisation allowlist for associated apps, differently per version; Android 16 removes the entry on every disconnect, including one the user set by hand.

Android 12-15 (updateSpecialAccessPermissionAsSystem, run at association time and on every package modification): if the manifest requests REQUEST_COMPANION_RUN_IN_BACKGROUND the package is added to the permanent power-save allowlist; otherwise it is REMOVED from it, which silently undoes a manual "Unrestricted" setting each time the app is updated. Android 16 and 16 QPR2 (CompanionExemptionProcessor.exemptPackage): added only while a device is present and the permission is requested; on disconnect and on package modification it calls removeFromPermanentAllowList() unconditionally. Android 17 adds CompanionExemptionStore to track user overrides and only removes entries CDM itself added. Any association also sets OP_AUTO_REVOKE_PERMISSIONS_IF_UNUSED to ignored, so the app is exempt from unused-app permission auto-revoke. The foreground-service-start exemption above is separate and unaffected. OEM battery managers (HyperOS "No restrictions", Samsung sleeping apps) are separate lists that CDM does not touch.

- Verifier: **confirmed**. ### 20. Facts about the manifest ACL_CONNECTED receiver that matter for the comparison.

ACTION_ACL_CONNECTED / ACTION_ACL_DISCONNECTED are on the implicit-broadcast exception list, so a manifest receiver is allowed. The stack sends them with receiver permission BLUETOOTH_CONNECT (the runtime permission must be granted or nothing arrives), with FLAG_RECEIVER_INCLUDE_BACKGROUND, and with FLAG_RECEIVER_REGISTERED_ONLY_BEFORE_BOOT (manifest receivers get nothing until boot has completed). They also carry BroadcastOptions.setTemporaryAppAllowlist(20 s default, TEMPORARY_ALLOW_LIST_TYPE_FOREGROUND_SERVICE_ALLOWED, REASON_BLUETOOTH_BROADCAST), which lets the receiver start a foreground service for about 20 s; this is in the source for Android 12, 14 and 17 but is not on the documented exemption list, so it should not be the only thing the app relies on. Since Android 13 the intent includes EXTRA_TRANSPORT. Not delivered to a force-stopped app; Android 17 collapses stale ACL broadcasts for the same device/transport to the most recent one.

- Confidence: high · Applies to: API 31-37
- Source: https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/android17-release/android/app/src/com/android/bluetooth/Util.kt
- Verifier: **confirmed**. Confirmed: on the implicit-broadcast exception list; sent with BLUETOOTH_CONNECT, FLAG_RECEIVER_INCLUDE_BACKGROUND, FLAG_RECEIVER_REGISTERED_ONLY_BEFORE_BOOT and a 20 s FOREGROUND_SERVICE_ALLOWED temp allowlist (android12 Utils.java, android17 Util.kt); EXTRA_TRANSPORT is API 33; android17 sets DELIVERY_GROUP_POLICY_MOST_RECENT keyed on transport/address (not in android16-release). Three nuances. (1) The delivery group covers CONNECTED and DISCONNECTED under one key, so an undelivered CONNECTED can be replaced by a later DISCONNECTED. (2) The before-boot flag only restricts delivery until the system's processes are ready; the practical loss is that a non-direct-boot-aware receiver gets nothing before the first unlock, with no replay, whereas CDM on Android 14+ replays at unlock. (3) Bluetooth is an updatable Mainline module on Android 16+, so these details can change with Play system updates. (https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/android17-release/android/app/src/com/android/bluetooth/btservice/RemoteDevices.java)

## What the verifier said the research missed

- Android 15 and 16 do not deliver any callback when startObservingDevicePresence is called while the truck is already connected: the service is bound but the event is dropped (added == false), and an association that was unobserved at connect time is ignored until the next reconnect. Android 13/14 (the target phone is Android 14) and Android 17 do deliver it. Onboarding done in the cab must therefore check the connection state itself rather than wait for CDM. Source: android15/16 devicepresence/DevicePresenceProcessor.java and BluetoothDeviceProcessor.java.
- There is no public ACL 'is connected' query on the target phone. BluetoothDevice.isConnected(int transport) only became public in version 36.1. On API 31-36.0 the app has to use BluetoothAdapter.getProfileConnectionState(HEADSET/A2DP) or a BluetoothHeadset/BluetoothA2dp profile proxy's getConnectedDevices(). This is needed for every case where no event arrives: reboot or app update with the truck already connected, the 14+ rebind after process death, the Android 15/16 onboarding gap, and confirming a legacy 'appeared' that may be a BLE sighting. Source: https://developer.android.com/reference/android/bluetooth/BluetoothDevice
- The user can delete the association from system Settings (Bluetooth device details page, companion apps section, Remove), present in AOSP Settings for Android 12, 14 and 17. The app is only told from version 36.1 (EVENT_ASSOCIATION_REMOVED). On the Android 14 target the app should compare getMyAssociations() against its stored truck on every launch and service start and prompt to re-associate.
- A genuinely independent second signal exists and was not mentioned: BluetoothHeadset.ACTION_CONNECTION_STATE_CHANGED and BluetoothA2dp.ACTION_CONNECTION_STATE_CHANGED are also on the implicit-broadcast exception list, so they can be manifest-registered. In android14 source both are sent with BLUETOOTH_CONNECT, FLAG_RECEIVER_INCLUDE_BACKGROUND and the same 20 s foreground-service temp allowlist. They come from the HFP/A2DP state machines, not from aclStateChangeCallback, so unlike the CDM/ACL pair they do not share a single call site, and they indicate a usable profile connection rather than a bare ACL link. Source: https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions
- The reference requires a runtime check of PackageManager.FEATURE_COMPANION_DEVICE_SETUP before calling the presence APIs. Whether HyperOS on the POCO X5 reports the feature is untested, so the app needs a working path with the ACL/profile receivers alone if it is absent.
- The companion pairing guide states that companion device pairing requires Location Services to be enabled. Onboarding error handling should account for location being off at association time. Source: https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing
- CompanionDeviceService delivers callbacks with postAtFrontOfQueue, so two callbacks that arrive while the main thread is busy (typical on a cold start) run in reverse order. A fast connect/disconnect flap can therefore be seen as disconnect-then-connect. Each callback should be treated as a hint to re-read real connection state, not as the state itself.
- On Android 16 and 17 CDM registers its Bluetooth connection callback at PHASE_BOOT_COMPLETED rather than PHASE_SYSTEM_SERVICES_READY, and the FGS-start exemption (companion UID set) is only pushed at user unlocking. Both make the first minutes after a reboot the weakest window for the CDM path.
- The findings contain no explicit recommendation, which the brief asked for. What the verified evidence supports: use the CDM association mainly for what only it provides (documented background FGS-start exemption independent of presence, restart of a force-stopped app on AOSP, replay at unlock on 14+, battery allowlist entry on 12-15 with REQUEST_COMPANION_RUN_IN_BACKGROUND), keep the manifest ACL receiver as a parallel delivery path and the required trip-end signal on Android 12/12L, add the HFP/A2DP profile broadcast as the independent detector, and confirm state through a profile proxy before starting or ending a trip. Whether HyperOS honours the system bind with Autostart off is the open question and needs a device test before CDM is treated as the primary trigger.

## Recommendations

- Use both mechanisms as equal, redundant triggers feeding one idempotent entry point (for example ensureTripRunning(reason)). Do not make CDM the only start path and do not treat it as the authority on connection state: it and ACL_CONNECTED share one upstream event, CDM has version-specific quirks, and its behaviour under HyperOS is unverified. Rely on CDM chiefly for what only it provides: starting a dead or force-stopped app via a direct system bind, the standing foreground-service-start exemption, the battery allowlist entry, and the auto-revoke exemption.
- Onboarding: after the owner picks the truck from the paired list, call associate() with BluetoothDeviceFilter.setAddress(truckMac) and setSingleDevice(true), no device profile. Branch at API 33 for the callback shape (onDeviceFound + EXTRA_DEVICE on 31-32; onAssociationPending/onAssociationCreated on 33+). Store the association id and MAC, then immediately start observing presence.
- Observation call by API level: 31-35 use startObservingDevicePresence(macAddressString) (the MAC, never the association id); 36+ use startObservingDevicePresence(ObservingDevicePresenceRequest.Builder().setAssociationId(id).build()). Do not swallow exceptions from this call; surface a failure in the permission checklist.
- Manifest: uses-feature android.software.companion_device_setup; REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE; REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND; REQUEST_COMPANION_RUN_IN_BACKGROUND (declare it: on Android 12-15 omitting it makes CDM remove the app from the battery allowlist on every reinstall); exactly one exported CompanionDeviceService guarded by BIND_COMPANION_DEVICE_SERVICE with the android.companion.CompanionDeviceService action. Skip REQUEST_COMPANION_USE_DATA_IN_BACKGROUND unless background network use on metered data turns out to be needed.
- In the CompanionDeviceService override all three generations (onDeviceAppeared(String), onDeviceAppeared(AssociationInfo) by leaving the default forwarding in place or overriding once, and onDevicePresenceEvent) and route them to the same idempotent handler. On API 36+ act on EVENT_BT_CONNECTED / EVENT_BT_DISCONNECTED and ignore BLE events. On API 31-35, where the source is not reported, confirm the truck is really connected (ACL receiver state or a Bluetooth profile proxy such as HEADSET/A2DP getConnectedDevices) before starting a trip.
- Start the app's own location foreground service straight from the callback and run the disconnect grace timer inside it. The CDM binding is not a foreground service and is dropped 0-5 s after disconnect on Android 13+, so it cannot carry the grace period.
- Treat ACL_DISCONNECTED as a first-class trip-end signal alongside CDM disappeared (accept whichever arrives first, then debounce with the grace period). This is mandatory on Android 12/12L, where CDM disappeared does not fire for connections under 10 minutes.
- Add recovery hooks that check 'is the truck connected right now?' and resume or start a trip: CompanionDeviceService.onCreate() (the system rebinds 10 s after process death on Android 14+ without re-sending appeared), BOOT_COMPLETED, MY_PACKAGE_REPLACED, and app launch. These cover reboot and app-update-while-connected, which neither trigger reports on its own.
- Require ACCESS_BACKGROUND_LOCATION (Allow all the time) in the permission checklist as a hard prerequisite for automatic starts; the CDM exemption does not let a location-type foreground service start from the background without it.
- On every app start, verify the association still exists (getMyAssociations on 33+, getAssociations on 31-32) and re-issue startObservingDevicePresence (a no-op if already observing). Show a checklist warning if the association is gone, which happens after uninstall or clearing data.
- Do not depend on the user-set battery 'Unrestricted' state for correctness on Android 16/16 QPR2, because CDM strips it at each disconnect there; depend on the association-based foreground-service exemption instead. On the Android 14 target phone, REQUEST_COMPANION_RUN_IN_BACKGROUND keeps the AOSP allowlist entry permanently, but the HyperOS Autostart and battery saver settings are separate and still need to be set by hand.
- Test on the POCO X5 before trusting either path: log every trigger with its source and timestamp in the event log; test with the app swiped away, force-stopped, after reboot before and after first unlock, and after a reinstall from Android Studio, each with HyperOS Autostart off and then on. Without the truck, 'adb shell cmd companiondevice simulate-device-appeared <associationId>' (Android 13+) and 'adb shell dumpsys companiondevice' exercise and inspect the CDM path.

## Questions raised for the owner

- After a phone restart, Android 14 holds the truck-connected event until the phone has been unlocked once. Is it acceptable that a trip started before that first unlock only begins recording when you unlock the phone, or do you need recording to start while the phone is still locked after a reboot?
- In your phone's Bluetooth settings, does the truck appear as one paired device or more than one (some head units show a separate entry for Android Auto or a second name)? If more than one, which entry shows as connected for calls/audio while you drive?
- Does the truck's stereo stay on and connected to the phone after you turn the ignition off (for example until a door opens), and do you ever sit in the parked truck with it connected for long stretches? This decides how the end-of-trip grace period should treat a connection that outlives the drive.
- Is this the only vehicle the app must detect, or do you sometimes drive a second or replacement work truck that should also start trips?
