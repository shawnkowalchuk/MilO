# Research: Android Auto screen with the Car App Library (sideloaded)

> Gathered 2026-10-03 by a research agent reading live primary sources. Every finding was then re-checked by an independent verifier; its verdict is shown on each finding.
> This file is evidence for the ADRs. It records what was true on that date and is not kept current.

## Summary

Research only; no project files were created or changed. Headline: the plan in docs/APP_ENCYCLOPEDIA.md and docs/FINDINGS_LOG.md ("Android Auto lists MilO once Unknown sources is on") is contradicted by Google's current documentation. Google states that the Unknown sources developer option does NOT apply to Car App Library (templated) apps, and that on a real vehicle an app must be installed from a trusted store (Google Play or ONE store); Internal App Sharing or an Internal Test Track are the sanctioned no-review routes. A build sideloaded from Android Studio will therefore show in the Desktop Head Unit (DHU) but, per Google, not on the truck. Nothing here was tested on the phone or truck (DHU is not installed on this Mac and no phone was attached).

Other answers in brief:
- Versions: latest stable of app, app-projected and app-testing is 1.7.0 (2025-07-16), read from Maven metadata. 1.8.0-rc01 (2026-08-26) and 1.9.0-alpha02 are newer but not stable; the 1.8.0-rc01 notes say it contains a security fix.
- Manifest: exported CarAppService with action androidx.car.app.CarAppService and one category; application-level com.google.android.gms.car.application -> @xml/automotive_app_desc with <uses name="template"/>; androidx.car.app.minCarApiLevel. No car-specific permission is needed for PaneTemplate. IOT is the least-wrong category.
- Template: PaneTemplate (minimum 4 rows guaranteed, max 2 actions). Keep row count and row titles constant and put the changing numbers in the row's secondary text, otherwise each update counts as a step toward the 5-template limit. MessageTemplate is unsuitable (any message change is a new step). Actions are tappable while driving unless wrapped in ParkedOnlyOnClickListener. The host throttles refreshes; no throttle period is published.
- Lifecycle: the car screen is not treated as foreground for location. The AOSP reference host binds on app start with BIND_INCLUDE_CAPABILITIES and unbinds non-navigation apps some seconds after the user leaves the app. Trip state must live in an app-scoped controller; Session/Screen only observe and send commands. Starting the location foreground service from the car button is legal only because MilO already plans background location plus battery-optimisation exemption / companion-device association.
- DHU: native Apple-silicon build exists (2.0 stable, 2.1 beta channel) via Android Studio SDK Manager.
- Xiaomi/HyperOS: only community-level evidence; mostly general background-kill and USB-install restrictions plus scattered Android Auto connection complaints.

Not confirmed: issuetracker.google.com could not be read (JavaScript/sign-in shell), so no issue-tracker evidence is included. Android Auto's own (closed-source) host behaviour for bind timing and capabilities is inferred from the AOSP reference host.

## Findings

### 1. Latest STABLE version of androidx.car.app:app, app-projected and app-testing is 1.7.0 for all three.

Raw maven-metadata.xml for each artifact (lastUpdated 20260909170450) ends: ... 1.7.0-rc01, 1.7.0, 1.8.0-alpha01..03, 1.8.0-beta01, 1.8.0-rc01, 1.9.0-alpha01, 1.9.0-alpha02. The <latest>/<release> tags point at 1.9.0-alpha02, so the tag cannot be used to pick a stable version. The release-notes page lists Stable 1.7.0 (July 16, 2025), RC 1.8.0-rc01 (August 26, 2026), Alpha 1.9.0-alpha02 (September 09, 2026). There are no 1.5 or 1.6 versions (numbering jumped from 1.4 to 1.7).

- Confidence: high · Applies to: Q1 versions
- Source: https://dl.google.com/android/maven2/androidx/car/app/app-projected/maven-metadata.xml

### 2. The published 1.7.0 artifact declares Car App API levels 1 through 8 (latest = 8); 1.9.0-alpha adds level 9.

I downloaded app-1.7.0.aar and inspected it: the car-app-api.level resource contains 8 and CarAppApiLevels has LEVEL_1..LEVEL_8. The reference page also shows LEVEL_8 'Added in 1.7.0' and LEVEL_9 'Added in 1.9.0-alpha02'. The release notes separately say the 1.7 naming was chosen 'to match the active CarApi version', so treat level 7 as the fully supported level and level 8 as present but mostly experimental in 1.7.0. Bundled defaults in the same AAR: content_limit_pane=4, content_limit_list=6, content_limit_grid=6. app-testing 1.7.0 pulls in Robolectric 4.14 as a runtime dependency. The library's own minSdk is 21 in 1.7.0 (moves to 23 in 1.8), so minSdk 31 is fine.

- Confidence: high · Applies to: Q1 versions
- Source: https://dl.google.com/android/maven2/androidx/car/app/app/1.7.0/app-1.7.0.aar

### 3. 1.8.0-rc01 release notes say it contains a security fix and tell users of lower versions to update, but it is a release candidate, not stable.

Verbatim: 'androidx.car.app:app-*:1.8.0-rc01 is released and has the same features as 1.8.0-beta01 ... This release includes a security fix. If you are using a lower version, please update to use this version.' The notes do not name the vulnerability. 1.7.0 is described as 'the first stable release that includes the fix for CVE-2024-10382'. This conflicts with the project rule of stable-only dependencies, so it is an owner decision.

- Confidence: high · Applies to: Q1 versions
- Source: https://developer.android.com/jetpack/androidx/releases/car-app

### 4. Manifest: an exported CarAppService with action androidx.car.app.CarAppService plus one category; application-level meta-data com.google.android.gms.car.application pointing at res/xml/automotive_app_desc.xml containing <uses name="template"/>; application-level meta-data androidx.car.app.minCarApiLevel.

Docs show: <service android:name=".MyCarAppService" android:exported="true"><intent-filter><action android:name="androidx.car.app.CarAppService"/><category android:name="androidx.car.app.category.POI"/></intent-filter></service>. The exported-without-permission lint warning is expected ('generally safe to ignore ... because you must override createHostValidator'). Label and icon on the <service> fall back to the <application> values. minCarApiLevel: <meta-data android:name="androidx.car.app.minCarApiLevel" android:value="1"/>. Android Auto declaration is in the second source: https://developer.android.com/training/cars/apps/auto

- Confidence: high · Applies to: Q2 manifest
- Source: https://developer.android.com/training/cars/apps/library/set-up-project

### 5. Category strings that exist today: NAVIGATION, POI, IOT, WEATHER, MEDIA, MESSAGING, CALLING in the docs table; the API reference additionally has SETTINGS and FEATURE_CLUSTER, and deprecated PARKING and CHARGING.

All are androidx.car.app.category.<NAME>. Reference annotations: IOT RequiresCarApi(6) ('declares physical objects with sensors, that connect and exchange data with other devices and systems'); WEATHER RequiresCarApi(7); MEDIA RequiresCarApi(8) and marked 'Added in 1.8.0'; MESSAGING and CALLING are @ExperimentalCarApi; SETTINGS RequiresCarApi(6) ('settings page and/or any error resolution screens'); PARKING and CHARGING deprecated in 1.3.0 in favour of POI. There is no category for trip logging, fleet or utilities.

- Confidence: high · Applies to: Q2 categories
- Source: https://developer.android.com/reference/androidx/car/app/CarAppService

### 6. IOT is the least-wrong category for a mileage tracker.

Quality guideline IT-1 allows an IoT app, while driving, to 'View the current state of devices' and offer 'Simple, one-touch features that control on and off functions', which is exactly a status pane with Start/End Trip. POI is for finding places; NAVIGATION implies turn-by-turn, navigation intents and the host treating MilO as a navigation app; WEATHER/MEDIA/MESSAGING/CALLING do not fit. This is my judgement from the category definitions, not a Google statement about mileage apps. Category quality rules only bite at Play review; Internal sharing and Internal testing tracks have form-factor review 'None' (https://developer.android.com/training/cars/distribute).

- Confidence: medium · Applies to: Q2 categories
- Source: https://developer.android.com/develop/adaptive-apps/quality-guidelines/car-app-quality

### 7. The category does not restrict the generic templates (Pane, Message, List, Grid); only map/navigation/media templates are gated, by manifest permission and in one case by category, and the host enforces that at runtime however the app was installed.

Docs: navigation templates require the androidx.car.app.NAVIGATION_TEMPLATES permission; PlaceListMapTemplate and MapWithContentTemplate require androidx.car.app.MAP_TEMPLATES, and 'PlaceListMapTemplate is available for use only by apps declaring the androidx.car.app.category.POI category'. In the AOSP reference host, TemplateChecker.checkPermissions is a no-op by default and only NavigationTemplateChecker / PlaceListMapTemplateChecker call CarAppPermission.checkHasLibraryPermission; PaneTemplateChecker has no permission check. So MilO needs no car-specific <uses-permission> for a PaneTemplate. The app's ordinary permissions (FOREGROUND_SERVICE, FOREGROUND_SERVICE_LOCATION, location, POST_NOTIFICATIONS) belong to the phone-side service, not the car screen.

- Confidence: medium · Applies to: Q2 templates vs category
- Source: https://developer.android.com/training/cars/apps/poi

### 8. SHOWSTOPPER FOR THE CURRENT PLAN: 'Unknown sources' in Android Auto developer settings does not apply to Car App Library apps, and a real vehicle requires installation from a trusted store.

Verbatim from Google: 'To test your app in real vehicles, you must install it from a trusted source such as Google Play, with one exception detailed in Allow unknown sources. You can use Internal App Sharing or an Internal Test Track to distribute your app to devices without going through the Google Play review process.' and 'Android Auto has a developer option that lets you run apps that aren't installed from a trusted source. This setting applies to media, messaging notifications, and parked apps but doesn't apply to apps built using the Android for Cars App Library.' The Android Auto platform page adds: 'apps must be installed from a trusted source to run on a real vehicle. Trusted sources include the following: Google Play, ONE store.' This contradicts the Edge-case note in docs/APP_ENCYCLOPEDIA.md (Android Auto screen) and the 2026-10-03 DECISION in docs/FINDINGS_LOG.md.

- Confidence: high · Applies to: Q3 sideloading
- Source: https://developer.android.com/training/cars/testing

### 9. A debug build signed with the debug key works in the Desktop Head Unit, but per Google's docs will not be listed on a real head unit unless it arrives via a trusted store. Internal App Sharing accepts debuggable builds signed with any key.

DHU: the car-samples README and the codelab install with adb and run in the DHU ('Enable the Android Developer Settings', 'Enable Unknown Sources in Android Auto', 'Run the DHU'). Real car via Play: Play Console Help says of Internal App Sharing 'You can upload and share debuggable app bundles or APKs', 'Uploaded artifacts ... can be signed with any key ... They're automatically re-signed with an Internal App Sharing key', 'Version codes don't need to be new or unique', 'Download links expire 60 days after the upload date'. Consequence: the Play-delivered copy has a different signature from an Android Studio debug install, so the two cannot update each other in place; switching between them means uninstalling (and losing the Room database unless exported). A Play Console account is required ($25 one-time, identity verification).

- Confidence: high · Applies to: Q3 sideloading
- Source: https://support.google.com/googleplay/android-developer/answer/9844679?hl=en

### 10. Android Auto form-factor review is 'None' for Internal sharing and Internal testing tracks, so a private personal app can reach the truck without Google reviewing it against the car quality guidelines.

Table on the distribution page: Internal sharing (Android Auto only): None; Internal testing: None; Closed testing: Non-blocking; Open testing: Blocking; Production: Blocking. Internal testing allows up to 100 testers and the app is not publicly listed. Play Console Help: 'Internal tests might not be subject to standard Play policy or security reviews.'

- Confidence: high · Applies to: Q3 sideloading
- Source: https://developer.android.com/training/cars/distribute

### 11. Community reports from August-September 2026 conflict on whether installer spoofing still gets a sideloaded template app onto a real head unit; treat it as unreliable.

(a) HomeCar issue #9: Google Play services CAR.VALIDATOR logs 'Package DENIED; ...'; reinstalling with 'adb install -i com.android.vending' and enabling Unknown sources made no difference on Android Auto 17.3 and 17.6 (that app used the legacy projection mechanism, not templates). (b) Vela issue #179 (a Car App Library navigation app): author says Unknown sources 'does nothing' for template apps and that 'adb install -i com.android.vending' failed, then on 2026-09-21 reported it working on a stock Pixel 9 using the third-party KingInstaller tool, but not on GrapheneOS. (c) A vendor blog (aaad-app.com) claims the -i trick works. (d) An open issue reports sideloaded apps not showing in Android Auto on a POCO X5 Pro with Android 14 HyperOS 1 (no details). None of this is from Google, none was tested on a POCO X5, and these tools are untrusted third-party APKs.

- Confidence: low · Applies to: Q3 sideloading
- Source: https://github.com/PimpinPumpkin/Vela/issues/179

### 12. Unknown sources still exists in Android Auto 17.x and still works for sideloaded MEDIA apps on a real car, which is the only officially sanctioned no-Play route to the truck screen.

Google's testing page says the option applies to media, messaging-notification and parked apps. A third-party project documented on 2026-09-30: 'Tested on a real car: playback works, and YP Music appears in the launcher once Unknown sources is on' (steps: tap Version about 10 times, overflow menu, Developer settings, Unknown sources, then Customize launcher if needed). A media-app shell is not what the owner asked for (he asked for the Car App Library), so this is only a fallback to decide on.

- Confidence: medium · Applies to: Q3 sideloading
- Source: https://github.com/SanuSanal/YouPipe-Music/pull/13

### 13. How to enable Android Auto developer mode (needed for the DHU, the debug overlay and Unknown sources).

Android 10+: Settings > Apps > Android Auto > Advanced > Additional settings in the app. Scroll to About, tap Version, then tap 'Version and permission info' 10 times and accept 'Allow development settings?'. Developer options then appear in the overflow menu (Developer settings, Start head unit server). 'Enable debug overlay' in Developer settings shows the current step count on screen, which is the direct way to verify refreshes are not consuming steps. Menu names on HyperOS may differ from Google's wording.

- Confidence: high · Applies to: Q3 and Q7
- Source: https://developer.android.com/training/cars/testing

### 14. Android developer verification (enforcement from 2026-09-30 in four countries, global in 2027) does not block installs from Android Studio/ADB.

FAQ: 'As a developer, you are free to install apps without verification with ADB.' and 'Apps installed using ADB won't require verification.' A free 'limited distribution account' (up to 20 devices, no ID) also exists. This affects phone installation only; it does not change the Android Auto trusted-store rule.

- Confidence: high · Applies to: Q3 sideloading
- Source: https://developer.android.com/developer-verification/guides/faq

### 15. HostValidator options: ALLOW_ALL_HOSTS_VALIDATOR, or HostValidator.Builder(context).addAllowedHost(package, sha256Digest) / addAllowedHosts(arrayRes).build(). The library ships androidx.car.app.R.array.hosts_allowlist_sample.

createHostValidator() is abstract, so it must be implemented. ALLOW_ALL_HOSTS_VALIDATOR: 'A host validator that doesn't block any hosts. This is intended to be used only during development.' On phones the TEMPLATE_RENDERER permission is not checked, so 'hosts must be allow-listed by signatures'. Documented pattern: if the app is debuggable return ALLOW_ALL_HOSTS_VALIDATOR, else Builder(...).addAllowedHosts(androidx.car.app.R.array.hosts_allowlist_sample). I inspected the 1.7.0 AAR: the sample allowlist contains three certificate digests for com.google.android.projection.gearhead (Android Auto) and three for com.google.android.apps.automotive.templates.host.

- Confidence: high · Applies to: Q4 host validation
- Source: https://developer.android.com/reference/androidx/car/app/validation/HostValidator

### 16. Safe choice for a personal build: use the hosts_allowlist_sample allowlist in every build type; fall back to ALLOW_ALL only temporarily if the DHU connection is rejected.

The service is exported with no permission, so with ALLOW_ALL any app on the phone could bind, read trip status and press Start/End Trip. The DHU is driven by the phone's real Android Auto app, so the allowlist should accept it as well as the truck. Risk: if Google rotates Android Auto's signing certificate, an old pinned library would reject the host until the library is updated; the host package and digest can be logged from the validator failure. That the DHU host is the gearhead package is my inference, not stated in the docs.

- Confidence: medium · Applies to: Q4 host validation
- Source: https://developer.android.com/reference/androidx/car/app/CarAppService

### 17. PaneTemplate is the best fit: at least 4 non-clickable information rows (each a title plus up to 2 text lines) and up to 2 action buttons, one of which can be primary.

PaneTemplate.Builder.build(): 'The number of items ... should be smaller or equal than the limit provided by CONTENT_LIMIT_TYPE_PANE. The host will ignore any rows over that limit. Each Row can add up to 2 lines of texts via addText and cannot contain either a Toggle or a OnClickListener. Up to 2 Actions are allowed in the Pane.' The bundled minimum for the pane limit is 4 (the host may allow more; query ConstraintManager.getContentLimit(CONTENT_LIMIT_TYPE_PANE)). Design guide: 'Up to 2 buttons, where one can be designated as primary', 'Up to 4 non-actionable rows (1 row is mandatory)'. Five values therefore need to be folded into 3 or 4 rows, for example Status / This trip (km and duration) / Today (sessions and km). Action.FLAG_PRIMARY needs Car API 4; header end-actions are a further 2 slots.

- Confidence: high · Applies to: Q5 templates
- Source: https://developer.android.com/reference/androidx/car/app/model/PaneTemplate.Builder

### 18. To refresh live km and duration without consuming steps, the pane's header title, the number of rows and every row TITLE must stay identical; put the changing values in the row's secondary text (addText). The action buttons may change freely.

PaneTemplate: 'this template is considered a refresh of a previous one if: The previous template is in a loading state, or The template title has not changed, and the number of rows and the title (not counting spans) of each row between the previous and new Panes have not changed.' The AOSP reference host confirms it in code: PaneTemplateChecker compares the template title, then CheckerUtils.rowsHaveSameContent compares only row.getTitle() strings. So a row titled '12.4 km' breaks the rule on every update, while title 'This trip' with text '12.4 km - 23 min' does not. Also keep the 'This trip' row present when idle (show a dash) so the row count never changes. If a non-refresh update happens five times, 'the host displays an error message to the user before closing the app'.

- Confidence: high · Applies to: Q5 templates
- Source: https://developer.android.com/reference/androidx/car/app/model/PaneTemplate

### 19. MessageTemplate is unsuitable for live values; ListTemplate and GridTemplate would work but fit worse; newer templates are not in stable.

MessageTemplate 'is considered a refresh of a previous one if the title and messages have not changed', so any change to the message text is a new step (max 2 body actions). ListTemplate (min 6 rows) and GridTemplate (min 6 items) have the same 'row/item titles unchanged' rule and are meant for selectable items. SectionedItemTemplate requires Car API 8 and arrives with 1.8 (beta/rc only); banners, chips and condensed items are 1.9 alpha. When 5 templates are used, only Navigation, Pane, Message, MediaPlayback, SignIn and LongMessage may be last. A single-screen app sits at step 1 permanently.

- Confidence: high · Applies to: Q5 templates
- Source: https://developer.android.com/reference/androidx/car/app/model/MessageTemplate

### 20. Pane actions are tappable while driving. Only listeners wrapped in ParkedOnlyOnClickListener are parked-only, and only SignInTemplate and LongMessageTemplate are parked-only templates.

ParkedOnlyOnClickListener: 'executes its onClick method only when the car is parked. When the car is not parked, the handler won't be executed and the host will display a message to the user ... Actions that direct the users to their phones must only execute while parked.' A plain Action.Builder().setOnClickListener { } has no such restriction and runs on the main thread. AOSP host TemplateValidator.isParkedOnlyTemplate lists only SignInTemplate and LongMessageTemplate. Start/End Trip do not send the user to the phone, so they should be plain listeners.

- Confidence: high · Applies to: Q5 templates
- Source: https://developer.android.com/reference/androidx/car/app/model/ParkedOnlyOnClickListener

### 21. invalidate() has no documented call limit, but the host throttles what reaches the screen and no throttle period is published; refreshes do not count as steps.

Screen.onGetTemplate: 'the host will throttle template updates to the car screen. When the app invalidates multiple times in a short period, the host will call this method for each call, but it may not update the actual car screen right away ... if the app sends the host two or more templates within a period of time shorter than the throttle period, only the last template will be displayed'. Screen.invalidate: no effect unless the screen is at least STARTED; 'subsequent calls have no effect until the new template is returned by onGetTemplate'; call it on the main thread. Design guidance: templated apps SHOULD 'Refresh content only for the purposes noted in Limiting driver distraction' and MAY 'Update a list row or grid item's ... secondary text to reflect changes'. I found no number of seconds in the docs or the AOSP host source. Practical reading: invalidate only when the displayed text actually changes (km rounded to 0.1, duration to whole minutes), which yields a few refreshes per minute.

- Confidence: medium · Applies to: Q5 refresh
- Source: https://developer.android.com/reference/androidx/car/app/Screen

### 22. PaneTemplate.Builder.setHeader(Header) is annotated RequiresCarApi(7) in 1.7.0; the older setTitle / setHeaderAction / setActionStrip are deprecated since 1.7.0.

Verified in the 1.7.0 class file and the reference page. Using the non-deprecated Header API therefore implies androidx.car.app.minCarApiLevel = 7 (or lint will flag it); using the deprecated setters allows minCarApiLevel = 1. The host's level comes from the Android Auto app on the phone, not the truck; 'if a host only supports API level 1, but a client app cannot run without features from API level 2 ... the apps shouldn't connect'. I did not confirm from a Google source which Car API level the current Android Auto release (17.x) negotiates; log carContext.carAppApiLevel on first run.

- Confidence: medium · Applies to: Q2 minCarApiLevel, Q5
- Source: https://developer.android.com/reference/androidx/car/app/model/PaneTemplate.Builder

### 23. The host creates the Session when the app is started on the car screen, not merely because the phone connected; for non-navigation apps the reference host unbinds again shortly after the user leaves the app.

Docs: onCreateSession 'is invoked the first time the app is started, or if the previous Session instance has been destroyed and the system has not yet destroyed this service'; Session ON_CREATE 'The session has just been launched'; ON_START 'The application is now visible in the car screen'; ON_STOP 'no longer visible'. AOSP reference host (CarAppBinding.java): bind(Intent) is called from CarHost.bindToApp with APP_START telemetry; on ON_STOP it posts MSG_UNBIND after CarHostConfig.getAppUnbindSeconds() ('how many seconds after the user leaves an app, should the system wait before unbinding'), and skips the unbind only when isNavigationApp(). Android Auto's own host is closed source; that it behaves the same is an inference. Design consequence: the car Session is short-lived and cannot be relied on to start or keep anything alive.

- Confidence: medium · Applies to: Q6 lifecycle
- Source: https://android.googlesource.com/platform/packages/apps/Car/Templates/+/refs/heads/main/Host/app/apphost/src/main/java/com/android/car/libraries/apphost/internal/CarAppBinding.java

### 24. Being shown on the car screen does NOT make the app foreground for location; Google says to use a foreground service in the same process as the CarAppService.

CarAppService class doc, 'Accessing Location': 'When the app is running in the car display, the system will not consider it as being in the foreground, and hence it will be considered in the background for the purpose of retrieving location ... To reliably get location for your car app, we recommended that you use a foreground service. If you have a service other than your CarAppService that accesses location, run the service and your CarAppService in the same process. Also note that accessing location may become unreliable when the phone is in the battery saver mode.' So do not put the CarAppService in a separate android:process.

- Confidence: high · Applies to: Q6 lifecycle
- Source: https://developer.android.com/reference/androidx/car/app/CarAppService

### 25. Starting the location foreground service from a car-screen button press is allowed on Android 14 only through the exemptions MilO already plans: background location granted, plus battery optimisation turned off or the companion-device permission.

Background-start rule (Android 12+): exemptions include 'The user turns off battery optimizations for your app' and 'Your app uses the Companion Device Manager and declares the REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND permission'. While-in-use rule (Android 14): 'you cannot create a location foreground service while your app is in the background, unless you've been granted the ACCESS_BACKGROUND_LOCATION runtime permission' (otherwise SecurityException; a missing start exemption gives ForegroundServiceStartNotAllowedException). The AOSP reference host binds with 'Context.BIND_AUTO_CREATE | Context.BIND_INCLUDE_CAPABILITIES' with the comment 'allows the "while-in-use" permission capabilities (e.g. location) in the app's process for the duration of the binding', but whether Android Auto's binding lifts the process state enough to count as an FGS-start exemption is not documented, so do not rely on it. Second source: https://developer.android.com/develop/background-work/services/fgs/service-types

- Confidence: medium · Applies to: Q6 lifecycle
- Source: https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start

### 26. Session and Screen are LifecycleOwners, so the Screen can collect an app-scoped StateFlow in a lifecycle-aware coroutine and call invalidate(); onGetTemplate should only read the latest cached value.

Session doc: 'implements LifecycleOwner'; Screen.getLifecycle: 'Use this Screen to observe androidx.lifecycle.LiveData s that may drive the backing data for your templates', 'Listeners that are added in ON_START, should be removed in ON_STOP'. With lifecycle-runtime-ktx this is lifecycleScope.launch { repeatOnLifecycle(Lifecycle.State.STARTED) { uiState.collect { invalidate() } } } on the main dispatcher (the lifecycleScope pattern is standard AndroidX, not shown in the car docs; the codelab only shows invalidate() from a click). Room queries should be exposed as Flow and converted to a StateFlow in the shared controller/repository, never queried inside onGetTemplate. The docs also say 'The host creates separate binder and CarContext instances per Session' and recommend 'a shared singleton' for cross-component communication, which supports one app-scoped trip controller used by both phone UI and car screen.

- Confidence: medium · Applies to: Q6 lifecycle
- Source: https://developer.android.com/reference/androidx/car/app/Session

### 27. CarConnection (already planned for 'do not end the trip while Android Auto is connected') works on Android 14 with library 1.3.0-beta01 or later, and car permission prompts need 1.7.0-rc01 or later.

Connection API page: for apps targeting Android 14+, 'use Car App Library version 1.3.0-beta01 or later. Earlier versions of the library throw an exception'. CarConnection(context).type is LiveData with CONNECTION_TYPE_NOT_CONNECTED / NATIVE / PROJECTION and can be observed from the phone-side service, independent of whether the car Session is bound. Request-permissions page: 'Update to androidx.car.app:1.7.0-rc01 or higher to ensure permission dialogs appear on Android 14 and higher (phone)'. 1.7.0 satisfies both.

- Confidence: high · Applies to: Q6 lifecycle
- Source: https://developer.android.com/training/cars/apps/library/connection-api

### 28. The Desktop Head Unit has a native Apple-silicon build: version 2.0 on the stable channel and 2.1 on the beta channel.

The SDK repository manifest lists package 'extras;google;auto' (Android Auto Desktop Head Unit Emulator) revision 2.0 (channel-0) with archive desktop-head-unit-darwin-aarch64_r02.0.zip and revision 2.1 (channel-1) with desktop-head-unit-darwin-aarch64_r02.1.zip, alongside darwin-x64, linux-x64 and windows-x64. The docs list extra library steps for Linux only; none for macOS. On this Mac the DHU is not yet installed (~/Library/Android/sdk/extras/google/auto does not exist) and the SDK has no cmdline-tools folder, so install through Android Studio's SDK Manager.

- Confidence: high · Applies to: Q7 DHU

### 29. DHU install and run steps on macOS.

## What the verifier said the research missed

- Gradle: declare BOTH androidx.car.app:app:1.7.0 and androidx.car.app:app-projected:1.7.0 (plus testImplementation app-testing:1.7.0). The app-projected 1.7.0 POM exposes 'app' only at runtime scope, so app-projected alone will not compile Screen/Session code; Google's own 'Declaring dependencies' snippet lists both. Source: https://dl.google.com/android/maven2/androidx/car/app/app-projected/1.7.0/app-projected-1.7.0.pom and https://developer.android.com/jetpack/androidx/releases/car-app
- Adaptive task limits changes the refresh rules and is not universal. Design guide: when the feature is NOT enabled 'Task flows must not exceed 5 steps, or the app will crash' and 'Refreshes are not throttled during drives'; it 'is not available for Japanese Automobile Manufacturers Association (JAMA)-affiliated Android Auto vehicles'. ConstraintManager.isAppDrivenRefreshEnabled() (@RequiresCarApi(6)) reports it. If the truck is a Japanese brand, the strict rule (fixed header title, fixed row count, fixed row titles) is the only safe design and the app must rate-limit its own invalidate() calls. Source: https://developer.android.com/design/ui/cars/guides/ux-requirements/plan-task-flows
- Button design rules that affect Start Trip / End Trip. Pane design page: 'Due to size constraints, the second action button's associated text is hidden and only its icon is shown', 'SHOULD Provide icons for all actions', 'SHOULD Designate a primary action when providing 2 actions'. UX requirements: 'SHOULD NOT Create buttons with states, such as toggles, in places where actions are supported'. So give both actions icons and short labels, and do not build one stateful toggle button. Source: https://developer.android.com/design/ui/cars/guides/templates/pane-template and https://developer.android.com/design/ui/cars/guides/ux-requirements/overview
- DistanceSpan and DurationSpan are available in 1.7.0 (Distance.UNIT_KILOMETERS_P1 gives one decimal place). Row.Builder.setTitle supports DistanceSpan/DurationSpan and addText supports them plus ForegroundCarColorSpan; the refresh comparison is on the string 'not counting spans' (AOSP carTextsHasSameString compares toString() only). The host then formats km and duration in the car's locale, and a span over a constant placeholder never breaks the refresh rule. Source: https://developer.android.com/reference/androidx/car/app/model/DistanceSpan
- If the Play internal route is chosen, three practical requirements were left out: (a) the phone's Play Store needs the hidden 'Internal app sharing' switch (tap Play Store version 7 times) and a link serves at most 100 users; (b) Play now requires new apps and updates to target Android 16 (API 36) as of August 31, 2026 (extension to November 1, 2026), the page does not say internal tracks are exempt; (c) Play Console has an Android Auto form-factor opt-in step. Sources: https://support.google.com/googleplay/android-developer/answer/9844679 , https://support.google.com/googleplay/android-developer/answer/11926878 , https://developer.android.com/training/cars/distribute
- Robolectric 4.14 (pulled in by app-testing 1.7.0) supports up to SDK 35 only ('Robolectric 4.14 adds support for Android V (SDK 35)'). If MilO targets API 36, car-screen unit tests using TestCarContext/SessionController need @Config(sdk = 35) or an explicitly pinned newer Robolectric. Source: https://github.com/robolectric/robolectric/releases/tag/robolectric-4.14
- The trusted-store rule does not block the rest of the plan: CarConnection works regardless of whether MilO's screen is listed (codelab: it 'has nothing to do with whether your own app is being displayed on the head unit'), so the 'do not end the trip while Android Auto is connected' guard and the DHU-tested screen can ship in a sideloaded build; only visibility on the real truck display depends on the install source. Source: https://developer.android.com/codelabs/car-app-library-fundamentals
- The car Session is disposable: the AOSP reference host unbinds a non-navigation app 180 seconds after it leaves the screen (app_unbind_delay_seconds). Every time the screen is opened it must rebuild from the shared trip controller, and Pane.Builder.setLoading(true) (no rows allowed while loading) is the legal first template if state is not ready; leaving a loading state counts as a refresh. Source: https://android.googlesource.com/platform/packages/apps/Car/Templates/+/refs/heads/main/Host/ and https://developer.android.com/reference/androidx/car/app/model/Pane.Builder
- DHU driving simulation needs 'restrict all' / 'restrict none' (Shift+U / U); speed, gear and parking_brake sensors are off by default and must be enabled under [sensors] in ~/.android/headunit.ini. Use 'restrict all' to check that Start/End Trip still respond while 'driving'. Source: https://developer.android.com/training/cars/testing/dhu
- Platform release notes relevant to the manifest: on Android 16, an app that opts into safer intents may need android:intentMatchingFlags="allowNullAction" on the CarAppService <service> or Android Auto cannot bind; on Android 14, opening anything on the phone from the car needs ActivityOptions with the phone display id (CarContext.requestPermissions in 1.7.0 already handles this). Source: https://developer.android.com/training/cars/platforms/releases
- Row text limits while driving: row title up to 2 lines, secondary text up to 2 lines, and longer secondary text 'will be truncated while driving'. Keep 'This trip' and 'Today' values on one short line each. Source: https://developer.android.com/design/ui/cars/guides/components/row

## Recommendations

- Do not start building on the assumption that Unknown sources will show MilO on the truck. Get the owner's decision first (see questions): Google's docs say a Car App Library app must come from a trusted store to appear on a real head unit. Correct the Android Auto entry in docs/APP_ENCYCLOPEDIA.md and add a FINDING to docs/FINDINGS_LOG.md when the build session starts.
- Dependencies, pinned exactly: androidx.car.app:app:1.7.0 and androidx.car.app:app-projected:1.7.0 as implementation, androidx.car.app:app-testing:1.7.0 as testImplementation (brings Robolectric 4.14). Let Renovate propose 1.8.0 when it goes stable; do not take 1.8.0-rc01 unless the owner accepts an RC for its security fix.
- Manifest: one exported service (the CarAppService) with action androidx.car.app.CarAppService and category androidx.car.app.category.IOT; application meta-data com.google.android.gms.car.application -> @xml/automotive_app_desc containing <automotiveApp><uses name="template"/></automotiveApp>; application meta-data androidx.car.app.minCarApiLevel = 7 if the non-deprecated Header API is used (1 if the deprecated setTitle/setHeaderAction are used). No car-specific uses-permission. Keep the CarAppService in the default process, the same one as the location foreground service.
- Host validation: return HostValidator.Builder(applicationContext).addAllowedHosts(androidx.car.app.R.array.hosts_allowlist_sample).build() in all build types; switch to ALLOW_ALL_HOSTS_VALIDATOR only as a temporary diagnostic if the DHU connection is refused, and log the rejected host.
- Screen: a single PaneTemplate that never pushes another screen. Fixed header title 'MilO'. Exactly three rows with constant titles and values in addText: 'Status' (Tracking - Business / Idle / Truck not connected), 'This trip' ('12.4 km - 23 min', or a dash when idle), 'Today' ('3 trips - 41.2 km'). One action whose label depends on state: 'Start Trip' when idle, 'End Trip' when tracking, flagged FLAG_PRIMARY, plain OnClickListener (not ParkedOnly). Never change the row count or row titles.
- Refresh: in the Screen's init, lifecycleScope.launch { repeatOnLifecycle(STARTED) { controller.carUiState.collect { invalidate() } } } on the main thread, where carUiState is a StateFlow of already-formatted strings with distinctUntilChanged (km to 0.1, duration to whole minutes). onGetTemplate reads carUiState.value only. During DHU testing turn on 'Enable debug overlay' in Android Auto developer settings and confirm the step count stays at 1 while values change.

## Questions raised for the owner

- Google's documentation says a sideloaded Car App Library app will not appear on a real head unit, even with Unknown sources on. Which route do you want? (a) Keep the Car App Library screen and deliver MilO to the phone through a private Google Play Internal App Sharing link or Internal Test Track (no review, not publicly listed, but needs a Play Console account: $25 one-time plus identity verification, and it contradicts 'never on Play Store'). (b) Stay sideload-only and accept that the Car App Library screen works only in the desktop emulator, not in the truck. (c) Stay sideload-only and replace the screen with a media-app style entry, which Unknown sources does allow on a real car, showing status as 'now playing' text with Start/End as buttons (a hack, and not the Car App Library you asked for). (d) Try an unofficial installer-spoofing tool such as KingInstaller at your own risk; reports are mixed and one says it fails on a POCO X5 Pro.
